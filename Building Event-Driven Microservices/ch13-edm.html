Building Event-Driven Microservices · Adam Bellemare · Chương 13

Microservices Framework Nhẹ

Kafka Streams — xử lý stream mạnh mẽ không cần cluster riêng, dựa vào event broker và CMS

Trong khi heavyweight framework (Chương 12) yêu cầu một cluster chuyên dụng riêng biệt, lightweight framework hoạt động theo mô hình hoàn toàn khác: không có dedicated cluster, không cần resource manager riêng — thay vào đó, chúng dựa hoàn toàn vào event broker và Cluster Management System (CMS) để cung cấp khả năng scaling, shuffling dữ liệu, và durability. Bạn deploy lightweight framework microservice như bất kỳ microservice nào khác trong hệ thống.

Ấn bản đầu tiên của cuốn sách này giới thiệu cả Kafka Streams lẫn Apache Samza. Đến ấn bản thứ hai này, Samza đã suy giảm đáng kể về độ phổ biến, số người dùng, và hoạt động của project. Kafka Streams hiện là lightweight framework duy nhất được sử dụng rộng rãi. Faust (Python) cũng được nhắc đến nhưng chưa đạt critical mass. Chương này tập trung vào Kafka Streams như đại diện chính của lightweight framework.

Ví Dụ Thực Tế: Join Sản Phẩm Với Dữ Liệu Thương Hiệu

Để hiểu Kafka Streams hoạt động như thế nào trong thực tế, hãy xem xét một use case phổ biến: enrichment qua foreign key join — kết hợp dữ liệu sản phẩm (Product) với dữ liệu thương hiệu (Brand) để tạo ra EnrichedProduct.

Tình huống (Hình 13-1): Một ecommerce database chứa hai bảng — Brands và Products. Hai connector riêng biệt convert dữ liệu từ database thành event stream: Brands stream (stream thương hiệu) và Products stream (stream sản phẩm). Mỗi product có trường brandId là foreign key tham chiếu đến Brand tương ứng. Nhiệm vụ là join hai stream này để tạo ra một stream EnrichedProduct chứa đầy đủ thông tin brand.

Code Kafka Streams (Ví Dụ 13-1)

public Topology buildTopology(Properties envProps) {
    // 1) Tạo Serde (Serializer/Deserializer)
    BrandSerde brandSerde = new BrandSerde(...);
    ProductSerde productSerde = new ProductSerde(...);
    EnrichedProductSerde enrichedProductSerde = new EnrichedProductSerde(...);

    // 2) Tạo stream builder
    KStreamBuilder builder = new KStreamBuilder();

    // 3) Khai báo hai KTable
    KTable<Long, Brand> brandTable =
        builder.table(Serdes.Long(), brandSerde, "brand-topic");
    KTable<Long, Product> productTable =
        builder.table(Serdes.Long(), productSerde, "product-topic");

    // 4) Khai báo join với joiner function
    productTable
        .join(brandTable, Product::getBrandId, new ProductToBrandJoiner())

    // 5) Chuyển về stream và ghi ra output
        .toStream()
        .to("enriched-product-topic",
            Produced.with(Serdes.Long(), enrichedProductSerde));

    // 6) Build và trả về topology
    return builder.build();
}

Code này làm rõ sự đơn giản của Kafka Streams API. Bước 1 khai báo các Serde — serializer/deserializer chuyển đổi byte array từ Kafka topic thành Java object (Brand, Product) và ngược lại. Có thể dùng Avro, Protobuf, hoặc JSON Schema.

Bước 3 là trọng tâm: khai báo hai KTable — một abstraction của Kafka Streams đại diện cho materialized view của một Kafka topic. KTable lưu state trong internal state store (RocksDB mặc định), tự động được cập nhật khi có event mới trên topic tương ứng. Key của KTable là brandId (Long) cho brandTable và productId (Long) cho productTable.

Bước 4 là table-to-table join: productTable.join(brandTable, Product::getBrandId, joiner) — với mỗi Product record, join với Brand record có cùng brandId (foreign key). Hàm joiner (ProductToBrandJoiner) nhận một cặp (Product, Brand) và trả về EnrichedProduct.

ProductToBrandJoiner (Ví Dụ 13-2)

public class ProductToBrandJoiner
    implements ValueJoiner<Product, Brand, EnrichedProduct> {

  public EnrichedProduct apply(Product p, Brand b) {
    return EnrichedProduct
        .newBuilder()
        .setId(p.getId())
        .setName(p.getName())
        .setDescription(p.getDescription())
        .setPrice(p.getPrice())
        .setBrandName(b.getBrandName())
        .setBrandLogoURI(b.getBrandLogoURI())
        .build();
  }
}

Đây là denormalization thuần túy: kết hợp Product data với Brand data thành một record phẳng EnrichedProduct, giúp downstream consumer không cần query riêng để lấy brand info.

Bước 5 convert kết quả join trở lại thành KStream và ghi ra enriched-product-topic. Bước cuối gọi builder.build() — Kafka Streams sẽ dùng topology này để start processing.

Điểm mạnh: lightweight framework như Kafka Streams cung cấp khả năng join, table materialization, foreign-key join, groupings, windowing, aggregation — tất cả các tính năng mà BPC pattern thiếu — mà không cần cluster riêng.

Bên Dưới Mui Xe: Cơ Chế Của Lightweight Framework

Bạn deploy lightweight framework microservice như bất kỳ event-driven microservice nào khác — dùng CMS native functions (Kubernetes deployment, replica set) để tăng/giảm parallelism bằng cách thêm hoặc bỏ instance. Không có secondary resource cluster nào (Flink/Spark) được đặt ở đâu đó để cung cấp durable state storage, failure recovery, hay scalability. Tất cả đều dựa vào event broker (Kafka) và, ở mức độ thấp hơn, CMS.

Event Shuffling Và Repartitioning

Khi cần repartition dữ liệu cho key-based operation (join, groupByKey, reduce/aggregation), lightweight framework không có external shuffle service như Spark. Thay vào đó, nó dùng internal event stream được host trên chính event broker.

Hình 13-2 minh họa: có hai input stream (P0 và P1). Microservice instances đọc từ input streams, rồi ghi event ra Internal stream theo đúng partition của key tương ứng (đây là repartition/shuffle). Sau đó, chính các instances đó đọc lại từ Internal stream để xử lý đúng key set của mình.

Internal streams là private — chỉ dùng nội bộ trong bounded context của microservice. Không bao giờ dùng internal stream để kết nối giữa các microservice khác nhau — làm vậy sẽ tạo ra coupling ngầm và phá vỡ boundary giữa các service.

Bằng cách dựa vào internal event stream trên event broker cho shuffling, lightweight application có thể scale dynamically — mọi in-flight event đều được lưu bền vững trong broker. Đánh đổi là tăng latency (không thể tránh được vì không có shuffle option nào khác). Kafka Streams, ví dụ, hoàn toàn bị ràng buộc vào Apache Kafka.

State Và Changelog

In-memory và disk-based key-value store là dạng state store phổ biến nhất trong lightweight framework — hoàn toàn có lý vì toàn bộ DSL (domain-specific language) của framework dựa trên việc thao tác và lưu trữ các cặp key-value.

Mặc định, lightweight framework dùng internal state store được backed bởi changelog stream lưu trên event broker. Changelog là cơ chế đã được mô tả trong Chương 8: mỗi thay đổi state được ghi ra changelog stream, cho phép state được rebuild từ đầu khi cần thiết (instance failure, scale up).

Framework cho phép plug in storage mode khác nhau — ví dụ, Kafka Streams có StateStore Interface để implement custom state store. Thay vì dùng RocksDB local, bạn có thể dùng Amazon DynamoDB làm backing store. Tuy nhiên, điều này thay đổi behavior của framework đáng kể và cần hiểu rõ trade-off.

Scaling Và Phục Hồi Sau Sự Cố

Scaling và recovering từ instance failure trong lightweight framework là hai quá trình rất giống nhau — cả hai đều đòi hỏi reassign partition và state. Đây là điểm khác biệt lớn so với heavyweight framework: không cần restart toàn bộ application để thay đổi parallelism.

Hình 13-3 minh họa quá trình scale up (từ 2 lên 3 instance):

  1. Scale up: Instance 2 mới được khởi động bởi CMS (Kubernetes tăng replica count).
  2. Rebalance input stream: Kafka consumer group rebalancing tự động reassign các partition (cả input stream và internal stream) cho 3 instances. Instance 2 nhận một subset partition từ Instance 0 và/hoặc Instance 1.
  3. Reload from changelog: Instance 2 phải load state của các partition vừa được assign từ changelog stream. Đây là giai đoạn state restoration — trong thời gian này, Instance 2 chưa xử lý event mới.

Có thể có delay xử lý trong giai đoạn rebalancing và rematerialization state. Khi một instance bị failure (thay vì intentional scale down), quá trình giống hệt: CMS phát hiện instance chết, khởi động instance thay thế, consumer group rebalance, state được reload từ changelog. Phần lớn quá trình này là tự động.

State Assignment Chi Tiết

Khi instance mới nhận partition assignment, nó phải load state trước khi xử lý event mới — tương tự cách heavyweight framework load checkpoint trước khi tiếp tục. Hai loại state:

Operator state (partitionId → offset): được lưu trong consumer group metadata trên Kafka broker. Đây là thông tin "đã đọc đến đâu" trong mỗi partition — cả partition input stream lẫn internal stream. Kafka broker quản lý consumer group offset, nên operator state tự động consistent sau rebalance.

Keyed state (key → state): được lưu trong changelog stream. Mỗi state store có changelog topic riêng. Instance mới phải consume toàn bộ changelog topic của partition được assign để rebuild local state store. Đây là bước tốn thời gian nhất trong state restoration.

Lưu ý quan trọng: Instance phải load toàn bộ stateful data trước khi xử lý event mới. Nếu xử lý event trong khi state chưa đầy đủ, kết quả có thể nondeterministic. Đây là state restoration phase — trong thời gian này, instance đang trong trạng thái "catching up", không xử lý event mới từ input stream.

State Replication Và Hot Replicas

Hot replica (giới thiệu trong Chương 8) là copy của state store — một instance đang theo dõi changelog của partition khác và giữ state đó trong local store của mình. Hot replica cung cấp fallback ngay lập tức khi primary instance serving data bị fail, và cho phép graceful scale-down stateful application.

Khi scale up có hot replica, workflow là:

  1. Start instance mới.
  2. Join consumer group, rebalance partition ownership.
  3. Pause trong khi state được materialized từ changelog — bước này có thể tốn thời gian.
  4. Resume processing.

Một option cải tiến: trước khi rebalance, populate một replica của state trên instance mới, đợi đến khi replica này caught up với đầu changelog, rồi mới trigger rebalance để assign partition cho instance mới. Cách này giảm outage do materializing từ changelog, và chỉ cần thêm bandwidth từ event broker. Tính năng này hiện đang được phát triển cho Kafka Streams.

Tổng Kết

Lightweight framework, với Kafka Streams là đại diện chính, cung cấp các tính năng xử lý stream nâng cao — joins, table materialization, windowing, aggregation — mà BPC pattern thiếu, nhưng không đòi hỏi dedicated cluster riêng như heavyweight framework. Thay vào đó, chúng tận dụng event broker (Kafka) và CMS để cung cấp scaling, data durability, và failure recovery.

Kafka Streams hiện là lightweight framework phổ biến nhất, dựa sâu vào Kafka để thực hiện xử lý dữ liệu quy mô lớn. Apache Samza, từng được giới thiệu cùng Kafka Streams trong ấn bản trước, đã giảm đáng kể về độ phổ biến và hoạt động project kể từ ấn bản đầu tiên.

Chương tiếp theo đi sâu hơn về lớp abstraction: Streaming SQL — cách viết streaming query bằng cú pháp SQL quen thuộc, chạy trên top của các framework như Flink và Spark.
