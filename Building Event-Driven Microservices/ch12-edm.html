Building Event-Driven Microservices · Adam Bellemare · Chương 12

Microservices Framework Hạng Nặng

Spark, Flink, Beam — kiến trúc cluster chuyên dụng, checkpointing, và chiến lược scaling cho xử lý stream quy mô lớn

Chương 12 bàn về các heavyweight framework — nhóm framework xử lý stream đòi hỏi một cluster chuyên dụng riêng biệt với hạ tầng event broker. Đây là các framework trưởng thành, được sử dụng rộng rãi trong phân tích dữ liệu quy mô lớn: Apache Spark Structured Streaming, Apache Flink, và Apache Beam. Dù mang lại sức mạnh vượt trội về khả năng xử lý phức tạp, chúng đến kèm với những đánh đổi quan trọng về mặt vận hành mà bất kỳ kiến trúc sư nào cũng phải cân nhắc kỹ.

Lịch Sử Phát Triển: Từ Hadoop Đến Spark/Flink/Beam

Để hiểu vì sao heavyweight framework tồn tại, cần nhìn lại lịch sử. Năm 2006, Apache Hadoop ra đời và mở ra kỷ nguyên xử lý dữ liệu lớn phân tán theo mô hình MapReduce. Hadoop cho phép xử lý petabyte dữ liệu bằng cách phân phối tính toán qua cluster máy chủ thông thường (commodity hardware). Nhưng MapReduce vốn là batch-processing — mỗi job phải đọc input từ đĩa, xử lý, ghi output ra đĩa, rồi job tiếp theo mới đọc — cực kỳ chậm cho các tác vụ lặp và interactive.

Apache Spark xuất hiện như một giải pháp thay thế nhanh hơn, với Resilient Distributed Dataset (RDD) giữ dữ liệu trong memory xuyên suốt nhiều bước xử lý. Spark sau đó phát triển thêm Spark Structured Streaming cho stream processing. Apache Flink, Apache Storm, Apache Heron — mỗi framework mang triết lý riêng, nhưng Flink đã nổi lên như lựa chọn stream-first mạnh mẽ nhất. Apache Beam ra đời như một API thống nhất có thể chạy trên nhiều execution engine (Flink, Spark, Google Dataflow).

Ấn bản đầu tiên của cuốn sách này còn nhắc đến Storm và Heron — nhưng tới nay cả hai đều đã bị thay thế. Trong số các heavyweight framework còn lại, Flink có tốc độ tăng trưởng nhanh nhất, Spark Structured Streaming vẫn rất phổ biến (đặc biệt trong hệ sinh thái Databricks), và Beam chủ yếu gắn với Google Cloud Dataflow.

Ba Đặc Điểm Định Nghĩa Heavyweight Framework

Điều phân biệt heavyweight framework với lightweight framework không phải là kích thước code hay số tính năng, mà là ba đặc điểm kiến trúc cốt lõi:

1. Dedicated cluster chuyên dụng. Heavyweight framework yêu cầu một cluster riêng biệt — hoàn toàn tách biệt với event broker cluster (Kafka, Pulsar). Cluster này có resource manager riêng, worker node riêng, và hạ tầng điều phối riêng. Đây là nguồn gốc của "overhead vận hành" mà heavyweight framework nổi tiếng.

2. Cơ chế nội bộ riêng. Heavyweight framework không phụ thuộc vào cơ chế của event broker cho state management, fault tolerance, hay scheduling. Chúng tự implement toàn bộ: internal state store, checkpointing, event scheduling, watermark. Framework kiểm soát hoàn toàn vòng đời của mỗi task.

3. Data shuffling tự động. Khi cần repartition dữ liệu (ví dụ group by một key khác), heavyweight framework tự động di chuyển dữ liệu qua mạng giữa các worker node mà không cần lập trình viên viết thêm code. Đây là tính năng then chốt cho các thao tác phức tạp như join nhiều stream, windowed aggregation.

Ví Dụ Thực Tế: Session Windowing Với Flink

Để hiểu heavyweight framework hoạt động như thế nào, hãy xem qua một use case thực tế: phân tích ad engagement — xác định xem người dùng có nhìn thấy quảng cáo rồi click vào sản phẩm đó trong một session 30 phút không.

Có hai input stream: Clicks (mỗi click của user vào product) và AdViews (mỗi lần user nhìn thấy quảng cáo). Output là AdEngagements — danh sách các session trong đó user vừa xem quảng cáo vừa click vào sản phẩm tương ứng trong cùng một session 30 phút.

Schema Của Hai Input Stream

Schema của Click event (Protobuf — Ví dụ 12-1):

message Click {
  string userId = 1;
  string productId = 2;
  string createdEventTime = 3;
}

Schema của AdView event (Protobuf — Ví dụ 12-2):

message AdView {
  string userId = 1;
  string adId = 2;
  string productId = 3;
  string createdEventTime = 4;
}

Flink Job Code

Toàn bộ join + windowing logic viết trong một đoạn Flink code ngắn gọn (Ví dụ 12-3):

eitherClicks
  .union(eitherViews)
  .keyBy(t -> productId)
  .window(EventTimeSessionWindows.withGap(Duration.ofMinutes(30)))
  .process(new ProcessClickViewWindowFunction())
  .addSink(new KafkaTopicSink(...))

Đây là sức mạnh của heavyweight framework: một pipeline stream processing phức tạp chỉ cần vài dòng khai báo. union() kết hợp hai stream, keyBy() nhóm theo productId, window() áp dụng session window 30 phút với event time, process() gọi hàm xử lý custom, addSink() ghi kết quả ra Kafka topic.

Hàm Xử Lý Window

Hàm ProcessClickViewWindowFunction (Ví dụ 12-4) nhận toàn bộ các event trong một window sau khi window đóng lại, rồi tìm cặp AdView + Click có cùng adId để xác định engagement:

class ProcessClickViewWindowFunction
    extends ProcessWindowFunction<Either, String, String, SessionWindow> {

  @Override
  public void process(String key,
                      Context context,
                      Iterable<Either> elements,
                      Collector<String> out) {

    List<AdView> adViews = new ArrayList<>();
    List<Click> clicks = new ArrayList<>();

    for (Either element : elements) {
      if (element.isLeft())  adViews.add((AdView) element.left());
      if (element.isRight()) clicks.add((Click) element.right());
    }

    List<String> adEngagements = new ArrayList<>();

    for (AdView adView : adViews) {
      for (Click click : clicks) {
        if (adView.adId.equals(click.productId)) {
          adEngagements.add(adView.adId);
        }
      }
    }

    if (!adEngagements.isEmpty()) {
      out.collect(String.join(",", adEngagements));
    }
  }
}

Output stream (Bảng 12-1): key là String userId, value là List<String> adEngagements — danh sách ad đã tạo ra engagement cho user đó trong session tương ứng.

Kiến Trúc Xử Lý Bên Dưới

Khi Flink chạy job trên, nó tạo ra một DAG (directed acyclic graph) gồm 3 stage (Hình 12-1):

Stage 1: Source — đọc từ Click và AdView Kafka topic, union thành một stream duy nhất.
Stage 2: Shuffle — keyBy(productId) trigger network shuffle: mỗi event được route đến đúng executor instance phụ trách productId đó. Đây là data shuffling tự động mà chỉ heavyweight framework mới làm được natively.
Stage 3: Window + Process + Sink — mỗi executor nhận các event cho subset productId của nó, tích lũy trong session window, sau khi window đóng thì chạy ProcessClickViewWindowFunction và ghi kết quả ra Kafka.

Mỗi executor instance lưu trạng thái window trong internal state store. Checkpoint state được chụp định kỳ để phục hồi khi failure (Hình 12-2 — khi scale down còn 1 instance, toàn bộ state được load lại từ checkpoint).

Kiến Trúc Nội Bộ: Resource Manager, Worker, ZooKeeper

Heavyweight cluster gồm ba thành phần chính (Hình 12-3):

Resource Manager (Master Node): Là bộ não của cluster. Resource manager nhận job submission, phân tích DAG, chia nhỏ thành các task, và assign các task đó đến worker node. Nó quản lý tài nguyên (CPU, memory) của toàn cluster, ưu tiên job theo policy, và theo dõi trạng thái của từng worker. Khi worker node gặp sự cố, resource manager phát hiện và reschedule các task bị ảnh hưởng sang worker khác. Resource manager luôn có một backup (standby) để tránh single point of failure.

Worker Node / Executor: Là nơi logic xử lý thực sự chạy. Mỗi worker node có thể chạy nhiều executor, mỗi executor là một JVM process thực hiện một phần của DAG. Executor lưu trữ internal state (keyed state) và operator state, tham gia vào quá trình checkpointing.

ZooKeeper: Cung cấp distributed consensus — dùng để bầu chọn resource manager leader (khi có primary và standby), lưu trữ cluster metadata, và đảm bảo các quyết định phân tán được thực hiện nhất quán. ZooKeeper là thành phần hạ tầng nền tảng cho nhiều hệ thống distributed khác nhau (Kafka cũng dùng ZooKeeper trong các phiên bản cũ).

Luồng xử lý (Hình 12-4): Lập trình viên submit job → resource manager nhận, phân tích, assign tasks → executors bắt đầu consume từ event stream → xử lý và ghi output ra event stream output.

Lợi Ích Của Heavyweight Framework

Heavyweight framework phù hợp hoàn hảo với một số use case quan trọng:

ETL và data transformation quy mô lớn: Chuyển đổi, làm sạch, enrich dữ liệu ở scale mà không framework nào khác làm được thuận tiện hơn.

Session windowing và window analysis phức tạp: Như ví dụ ad engagement trên — join nhiều stream theo thời gian, với window logic phức tạp. Đây là use case heavyweight framework trội nhất.

Anomaly detection và machine learning online: Detect bất thường trong stream real-time, hoặc áp dụng ML model trực tiếp vào pipeline stream.

Aggregation quy mô lớn: Group by nhiều key, aggregate theo nhiều dimension, join cross-stream — tất cả đều được hỗ trợ natively.

Stateless transformation đơn giản: Dù không cần cluster riêng cho stateless ops, heavyweight framework vẫn làm tốt và dễ scale.

Ngoài ra, các framework này đều trưởng thành, có documentation đầy đủ, cộng đồng lớn, và được battle-tested trong production tại hàng ngàn công ty trên thế giới.

Hạn Chế Của Heavyweight Framework

Ba hạn chế cốt lõi cần nắm rõ trước khi chọn heavyweight framework:

1. Không Phải Microservice-Style Deployment Theo Mặc Định

Khi deploy một job lên Flink hay Spark cluster, job đó không được coi là một microservice độc lập theo nghĩa truyền thống — nó là một application chạy trong cluster dùng chung với các job khác. Ranh giới ownership và deployment cycle trở nên phức tạp hơn khi nhiều team cùng dùng một cluster.

2. Hạn Chế Ngôn Ngữ

Lịch sử, Spark và Flink được viết cho JVM: Java và Scala là first-class citizen. Python support (PySpark, PyFlink) đã cải thiện đáng kể nhưng vẫn không hoàn toàn tương đương. Go, Ruby, Rust — gần như không có support native. Điều này là rào cản lớn cho các team không dùng JVM stack.

3. Không Hỗ Trợ Indefinite Table Materialization Natively

Heavyweight framework tối ưu cho windowed processing — tức là dữ liệu được xử lý trong các cửa sổ thời gian rồi giải phóng. Nếu muốn materialize một bảng vô thời hạn (giữ trạng thái mãi mãi không có window), framework không hỗ trợ trực tiếp. Workaround phổ biến: dùng global window với custom trigger — nhưng phức tạp và không phải native use case.

Hệ quả: joins là acid test cho khả năng của một framework. Join hai stream trong heavyweight framework đòi hỏi window, state management, và data shuffling đồng thời. Nếu join không có window (join vô hạn), cần workaround. Khả năng join của framework thường là thước đo tốt nhất để đánh giá độ trưởng thành.

Thiết Lập Cluster

Hosted Service — Lựa Chọn Đơn Giản Nhất

Cách ít đau đầu nhất: dùng managed service do cloud provider hoặc vendor cung cấp:

  • Confluent Platform: Managed Flink trên cloud (tích hợp chặt với Kafka)
  • AWS Managed Service for Apache Flink (trước đây là Kinesis Data Analytics)
  • Google Cloud Dataflow (chạy Apache Beam)
  • Databricks (managed Spark, rất phổ biến trong data engineering)
  • Microsoft Azure HDInsight / Synapse Analytics (managed Spark)

Với managed service, team không cần lo về provisioning cluster, upgrading framework, hay xử lý node failure — tất cả do vendor lo. Đánh đổi là vendor lock-in và chi phí cao hơn tự host.

Tự Host: Mode 1 — CMS-Provisioned Cluster

Trong Mode 1, Cluster Management System (CMS — Kubernetes, Mesos, hoặc custom provisioner) tạo và quản lý cluster cho tất cả heavyweight framework jobs. Resource manager (JobManager trong Flink, Master trong Spark) chạy trong container do CMS quản lý. Worker node cũng chạy trong container. Tất cả job share cùng cluster.

Ưu điểm: tập trung, dễ monitor tổng thể. Nhược điểm: một team có thể ảnh hưởng performance của team khác (noisy neighbor problem), upgrade cluster ảnh hưởng toàn bộ job.

Tự Host: Mode 2 — Kubernetes Làm Resource Manager (Hình 12-5)

Mode 2 hiện đại hơn: mỗi job có cluster riêng, với Kubernetes đóng vai trò resource manager cấp cao nhất. Flink native Kubernetes integration và Spark on Kubernetes đều hỗ trợ mode này. Mỗi job submit tạo ra một namespace/deployment Kubernetes riêng với resource manager container và worker container của riêng nó.

Ưu điểm: isolation hoàn toàn giữa các job, mỗi team tự quản lý cluster của mình, upgrade một job không ảnh hưởng job khác. Nhược điểm: tăng resource overhead (mỗi job có resource manager riêng), cần Kubernetes expertise cao.

Application Submission: Driver Mode Vs Cluster Mode

Driver Mode

Trong Driver Mode, một local coordinator process (driver) chạy trên máy submit job. Driver phân tích DAG, chia task, và điều phối execution. Executors vẫn chạy trong cluster, nhưng driver nằm ngoài.

Flink và Spark đều hỗ trợ Driver Mode. Một điểm quan trọng: driver process có thể được deploy như một microservice — chạy trong container, quản lý bởi CMS như bất kỳ microservice nào khác. Đây là cách heavyweight framework job tích hợp gọn vào kiến trúc microservice.

Nhược điểm: nếu driver process crash, toàn bộ application bị ảnh hưởng. Cần HA strategy cho driver (restart policy trong Kubernetes).

Cluster Mode

Trong Cluster Mode, toàn bộ application được submit lên cluster — bao gồm cả coordinator logic. Cluster cấp một unique ID cho application và quản lý toàn bộ lifecycle. Lập trình viên tương tác với application qua cluster API (submit job, monitor, cancel).

Cluster Mode phù hợp khi job cần chạy rất lâu dài, không gắn với lifecycle của máy submit. Kubernetes operator cho Flink và Spark hỗ trợ Cluster Mode với tích hợp native.

State Và Checkpointing

State management là một trong những điểm mạnh nhất của heavyweight framework. Hiểu rõ cơ chế checkpoint là chìa khóa để vận hành hiệu quả.

Hai Loại State

Heavyweight framework quản lý hai loại state (Hình 12-6):

Operator State: Trạng thái gắn với một operator instance cụ thể, không phụ thuộc key. Ví dụ quan trọng nhất: partitionId → offset mapping — operator source lưu biết nó đã đọc đến đâu trong mỗi Kafka partition. Đây là dữ liệu cần thiết để sau khi failure, operator biết tiếp tục từ đúng vị trí.

Keyed State: Trạng thái gắn với một key cụ thể — ví dụ window state cho mỗi productId, hay aggregation state cho mỗi userId. Keyed state được phân phối theo key: executor A phụ trách key set A, executor B phụ trách key set B. Sau khi shuffle (keyBy), mỗi executor chỉ thấy keys của mình.

Checkpoint Là Gì Và Hoạt Động Như Thế Nào

Checkpoint là một snapshot đồng bộ của toàn bộ state tại một thời điểm nhất định. Framework trigger checkpoint định kỳ (configurable interval). Quá trình:

  1. Framework inject barrier marker vào input stream.
  2. Khi executor nhận được barrier, nó snapshot toàn bộ state hiện tại (operator state + keyed state).
  3. Snapshot được ghi ra cloud storage (S3, GCS, Azure Blob Storage) hoặc HDFS.
  4. Sau khi tất cả executor confirm đã checkpoint, toàn bộ checkpoint được đánh dấu complete.

Khi failure xảy ra: framework load checkpoint gần nhất từ cloud storage, restart các executor, và tiếp tục xử lý từ offset được lưu trong operator state. Mọi event từ offset đó đến thời điểm failure có thể được xử lý lại — đây là cơ sở của at-least-once và exactly-once semantic trong heavyweight framework.

Quan trọng: Framework phải load toàn bộ state vào memory/disk trước khi bắt đầu xử lý event mới. Với state store lớn (hàng chục GB), thời gian khởi động sau failure có thể lên đến nhiều phút.

Thực tiễn tốt: ưu tiên dùng internal state của framework (không phải external database) để tận dụng tối đa cơ chế checkpoint tự động và recovery đảm bảo.

Chiến Lược Scaling

Scaling Stateless: Đơn Giản

Với stateless operation (map, filter, simple transform), scaling chỉ là thêm executor instance. Không có state để phân phối lại, không có shuffle issue. Consumer group rebalancing trong Kafka lo phần còn lại. Đơn giản và nhanh.

Scaling Stateful: Hai Chiến Lược

Chiến lược 1 — Scale by Restart (Hình 12-8):

  1. Pause input stream (hoặc cho job catch up hết backlog)
  2. Trigger checkpoint để lưu toàn bộ state hiện tại
  3. Stop job
  4. Restart với parallelism mới (nhiều hoặc ít executor hơn)
  5. Framework load state từ checkpoint, redistribute keyed state sang số lượng executor mới
  6. Job tiếp tục xử lý

Quá trình này an toàn và đảm bảo correctness, nhưng có downtime. Một thách thức quan trọng là state redistribution + shuffle reconfiguration: khi parallelism thay đổi, keyed state phải được redistribute (key set nào về executor nào). Và sau khi thêm executor, consumer group rebalancing trigger data shuffle mới qua network — có thể tạo ra spike tải ngắn hạn.

Chiến lược 2 — Scale While Running:

Apache Spark có External Shuffle Service (ESS) — một process riêng chạy trên mỗi worker node, phụ trách shuffle data thay vì executor. Khi executor thêm hoặc bỏ, ESS tiếp tục phục vụ shuffle data mà không cần restart. Spark có thể tận dụng ESS để scale số executor trong khi job đang chạy (Hình 12-9/12-10: Dynamic Resource Allocation). Spark lắng nghe backlog metrics, nếu backlog tăng thì yêu cầu thêm executor từ resource manager, nếu giảm thì trả bớt executor.

Apache Flink có Adaptive Scheduler và Declarative Resource Management — thay vì yêu cầu đúng số executor cụ thể, job khai báo "cần ít nhất X, tối đa Y executor" và Flink tự điều chỉnh trong range đó dựa trên availability. Flink cũng đang phát triển reactive scaling để tự động điều chỉnh parallelism dựa trên metrics.

Autoscaling

Autoscaling là mục tiêu lý tưởng: framework tự động scale lên/xuống dựa trên load thực tế mà không cần operator can thiệp. Các metrics phổ biến dùng để trigger autoscaling:

  • Consumer lag: Nếu lag tăng, cần thêm processing capacity
  • End-to-end latency: Nếu latency vượt SLA, scale up
  • CPU và memory utilization: Metrics truyền thống của infrastructure

Một số framework đã tích hợp sẵn autoscaling: Google Cloud Dataflow có horizontal autoscaling built-in khá trưởng thành. Spark với Dynamic Resource Allocation gần với autoscaling. Flink Reactive Mode cũng hướng đến đây. Tuy nhiên, autoscaling cho stateful streaming vẫn còn ở giai đoạn phát triển với nhiều thách thức chưa giải quyết hoàn toàn (như state redistribution trong khi scale).

Với các framework chưa có built-in autoscaling, cần external wiring: một controller bên ngoài (ví dụ KEDA trên Kubernetes, hoặc custom controller) lắng nghe metrics và gọi cluster API để điều chỉnh parallelism.

Phục Hồi Sau Sự Cố

Heavyweight framework được thiết kế để tự phục hồi từ các loại failure phổ biến:

Worker node failure: Resource manager phát hiện worker bị mất (qua heartbeat timeout). Các task đang chạy trên worker đó được reschedule sang các worker còn lại. State của các task bị ảnh hưởng được load lại từ checkpoint gần nhất. Processing tiếp tục từ checkpoint — có reprocessing một phần event (at-least-once), nhưng với barrier snapshotting đúng cách có thể đạt exactly-once.

Resource manager failure: Đây là trường hợp nghiêm trọng hơn. Để xử lý, resource manager luôn có một standby instance. ZooKeeper được dùng để bầu chọn leader: khi primary resource manager crash, standby được bầu làm primary ngay lập tức. Cluster tiếp tục hoạt động với interruption ngắn.

Monitoring là cực kỳ quan trọng trong heavyweight cluster. Cần thiết lập alert cho: executor failure rate, checkpoint failure/lag, consumer lag, memory pressure. Việc phát hiện sớm sự cố ngăn chặn cascade failure ảnh hưởng toàn cluster.

Multitenancy

Khi nhiều team cùng dùng một heavyweight cluster, multitenancy trở thành vấn đề cần thiết kế cẩn thận.

Phương án 1 — Nhiều cluster nhỏ hơn: Mỗi team hoặc business unit có cluster riêng. Isolation hoàn toàn — team A không thể ảnh hưởng team B. Nhưng tổng resource overhead tăng (mỗi cluster cần resource manager, ZooKeeper). Phù hợp khi team có SLA nghiêm ngặt và cần đảm bảo không bị ảnh hưởng bởi team khác.

Phương án 2 — Namespacing trên cluster chung: Một cluster lớn với namespace riêng cho mỗi team. Resource quotas được set per namespace (ví dụ team A tối đa 100 CPU core, team B tối đa 200). Priority classes quyết định job nào được ưu tiên khi resource khan hiếm. Phức tạp hơn để quản lý nhưng hiệu quả resource cao hơn.

Resource acquisition priority: Trong cluster chung, cần có policy rõ ràng: job production critical có priority cao nhất, job batch ETL priority thấp hơn, job development/testing chỉ dùng idle resource. Framework như Flink hỗ trợ priority scheduling, Yarn và Kubernetes cũng có priority class mechanism.

Ngôn Ngữ Lập Trình Được Hỗ Trợ

Như đã đề cập, hạn chế ngôn ngữ là rào cản thực tế của heavyweight framework. Nhìn theo thực tế hiện tại:

Java và Scala: First-class citizen trong tất cả heavyweight framework. API đầy đủ nhất, performance tốt nhất, documentation phong phú nhất.

Python: PySpark và PyFlink đã trưởng thành đáng kể và được dùng rộng rãi trong data science/ML pipeline. Tuy nhiên, Python API vẫn có một số tính năng advanced chưa được expose đầy đủ, và performance overhead của Python UDF (nếu dùng) đáng kể hơn Java/Scala.

Go, Rust, JavaScript, Ruby, C#: Không có official support native. Beam có một số language SDK thử nghiệm (Go SDK), nhưng không widespread.

Kết quả thực tế: nếu team chủ yếu dùng Java/Scala hoặc Python, heavyweight framework là lựa chọn khả thi. Nếu team dùng Go, Rust, hay đa ngôn ngữ — lightweight framework hoặc BPC pattern phù hợp hơn.

Chọn Framework Nào?

Trong số các heavyweight framework còn tích cực phát triển:

Apache Flink: Lựa chọn hàng đầu cho stream processing thuần túy. Flink được thiết kế từ đầu cho streaming (không phải batch-first như Spark), hỗ trợ event time và watermark native, stateful processing mạnh mẽ, và có tốc độ adoption nhanh nhất trong cộng đồng. Nếu không có ràng buộc đặc biệt, Flink là default choice cho heavyweight stream processing.

Apache Spark Structured Streaming: Rất phổ biến, đặc biệt trong hệ sinh thái Databricks và các tổ chức đã dùng Spark cho batch processing. Thêm Structured Streaming vào Spark cluster sẵn có là con đường tự nhiên. Spark có ecosystem cực kỳ phong phú (MLlib, GraphX, SQL).

Apache Beam: Phù hợp khi cần portability — viết một lần, chạy trên nhiều execution engine. Beam pipeline có thể chạy trên Flink, Spark, hoặc Google Cloud Dataflow. Trong thực tế, Beam chủ yếu gắn với Dataflow. Nếu team muốn vendor-neutral API với option chuyển sang Dataflow sau, Beam là lựa chọn.

Tổng Kết

Heavyweight framework là công cụ mạnh mẽ cho các use case phân tích stream quy mô lớn: session windowing, cross-stream join, anomaly detection, ETL phức tạp. Với cluster architecture trưởng thành, checkpointing, data shuffling tự động — chúng làm được những thứ mà lightweight framework và BPC pattern không thể xử lý hiệu quả.

Nhưng "heavyweight" không chỉ là tên gọi — chúng thực sự mang lại operational overhead đáng kể: cluster riêng cần quản lý, hạn chế ngôn ngữ, deployment model không hoàn toàn microservice-native (dù đang cải thiện với Kubernetes integration), và không phải mọi pattern microservice đều cần tới sức mạnh này.

Quyết định dùng heavyweight framework nên dựa trên câu hỏi: use case có thực sự cần khả năng mà chỉ heavyweight mới cung cấp không — cross-stream join với windowing, data shuffling tự động, stateful aggregation phức tạp ở scale lớn? Nếu có, heavyweight framework là lựa chọn tốt. Nếu không, lightweight framework (Kafka Streams) hoặc BPC pattern sẽ mang lại cùng kết quả với ít overhead hơn nhiều. Chương tiếp theo sẽ khám phá thế giới lightweight framework.
