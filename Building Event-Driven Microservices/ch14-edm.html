Streaming SQL

Truy vấn stream bằng cú pháp SQL khai báo — continuous query, stream-as-table, và UDF tùy chỉnh

Streaming SQL là cơ chế khai báo (declarative) để xây dựng microservice-like query. Thay vì viết code Java/Python để xử lý từng event, bạn mô tả kết quả bạn muốn bằng cú pháp SQL quen thuộc — SQL engine sẽ lo phần implementation bên dưới. Đây là cách giảm đáng kể overhead khi bắt đầu với stream processing, đặc biệt phù hợp với những ai đã quen với SQL truyền thống.

Streaming SQL phổ biến nhất được implement như một layer trên top của heavyweight framework: Apache Flink cung cấp Flink SQL, Apache Spark cung cấp Spark SQL (trong Structured Streaming). Các framework khác cũng có SQL API trên streaming engine của họ.

Một lưu ý quan trọng: hiện tại không có chuẩn Streaming SQL thống nhất (ANSI hay bất kỳ chuẩn nào khác). Đây là "vùng hoang dã" — mỗi framework có dialect riêng với syntax và semantics khác nhau. Nhưng các khái niệm nền tảng đều nhất quán, và syntax không quá khác biệt để không thể học được khi chuyển framework.

Continuous Query — Nền Tảng Của Streaming SQL

SQL truyền thống hoạt động trên bảng (table) trong database — bạn chạy một query, nó đọc dữ liệu tại thời điểm đó, trả về kết quả, rồi kết thúc. Streaming SQL lấy lại SQL quen thuộc này và áp dụng cho event stream.

Hình 14-1 minh họa một streaming SQL query đơn giản nhất: lọc ra các event có value ≤ 5.

SELECT *
FROM input_stream
WHERE value > 5;

Stream input_stream chứa các event [1, 4, 8, 7, 3]. Query trả về output [8, 7] — chỉ những event có value > 5. Sự khác biệt then chốt: streaming SQL query chạy vô thời hạn — không kết thúc sau khi xử lý xong batch dữ liệu, mà tiếp tục lắng nghe và xử lý event mới khi chúng đến. Trong khi đó, query SQL truyền thống kết thúc sau khi đã iterate qua dataset có giới hạn của nó.

Cả hai đều hoạt động trên table — streaming SQL cũng vậy, chỉ là table được tạo ra từ event stream chứ không phải database tĩnh. Bước đầu tiên bắt buộc khi dùng Streaming SQL là khai báo table trên top của stream.

Ba Loại Table Trong Streaming SQL

Khi khai báo một table từ event stream, có ba loại table chính:

1. Upsert Table

Upsert table yêu cầu primary key. Mỗi event là một upsert hoặc delete — event mới có cùng key sẽ ghi đè record cũ. Đây là loại table phổ biến nhất, giống hệt với materialized table từ entity events được mô tả trong Chương 2. Phù hợp cho việc track trạng thái hiện tại của entity (user profile, product info, order status).

2. Append-Only Table

Append-only table không yêu cầu primary key. Mỗi event chỉ được insert, không bao giờ bị update hay delete — record là immutable. Đây là history đầy đủ của tất cả event, giống như chính append-only log backing event stream. Phù hợp cho audit log, event history, hoặc khi cần giữ toàn bộ lịch sử thay đổi.

3. Retraction Table

Retraction table là loại nâng cao hơn — không phải mọi streaming SQL framework đều hỗ trợ. Nó hỗ trợ insert, update, và delete, với toàn bộ row đóng vai trò key. Insert một row qua event +I["Gary", 123], xóa qua event +D["Gary", 123]. Retraction table chủ yếu dùng để phản ánh kết quả của upstream computation — ví dụ khi emit event từ Flink dynamic table.

Thực tiễn tốt: Đảm bảo framework bạn chọn hỗ trợ ít nhất append-only và upsert table. Một số framework chỉ hỗ trợ append-only, điều này sẽ hạn chế đáng kể khả năng xử lý.

Ví Dụ: Enrich Dữ Liệu Bằng Flink SQL

Hãy xem qua một ví dụ đầy đủ: join bảng Photographs với bảng Photographers để tạo ra EnrichedPhotographs — mỗi ảnh được enrich với thông tin đầy đủ của nhiếp ảnh gia.

Khai Báo Table Photographs

CREATE TABLE Photographs (
  id BIGINT PRIMARY KEY NOT ENFORCED,
  photographer_id BIGINT NOT NULL,
  camera_id BIGINT NOT NULL,
  photo_url STRING NOT NULL,
  height INT,
  width INT
) WITH (
  'connector' = 'upsert-kafka',
  'topic' = 'Photographs',
  'key.format' = 'raw',
  'value.format' = 'json',
  'properties.bootstrap.servers' = 'broker.url:9092',
  'properties.group.id' = 'Photographs_group_id'
);

Flink SQL đọc cú pháp CREATE TABLE này và đăng ký table definition vào metadata catalog — catalog cho phép các streaming SQL engine khác cũng query table này. Framework tạo Photographs table bằng upsert-kafka connector — event mới trên topic được upsert vào table (key trùng thì overwrite).

Lưu ý: primary key được đặt là NOT ENFORCED — vì data ownership thuộc về producer service ghi vào Photographs topic, không thuộc về Flink job. Enforcement tính toàn vẹn là trách nhiệm của producer.

Khai Báo Table Photographers (Với Avro Schema Registry)

CREATE TABLE Photographers (
  kafka_key_id BIGINT PRIMARY KEY NOT ENFORCED,
  first_name STRING,
  last_name STRING,
  signup_date TIMESTAMP WITH TIME ZONE
) WITH (
  'connector' = 'upsert-kafka',
  'topic' = 'Photographers',
  'properties.bootstrap.servers' = 'broker.url:9092',
  'properties.group.id' = 'Photographers_group_id',
  'key.format' = 'raw',
  'key.fields' = 'kafka_key_id',
  'value.avro-confluent.url' = 'http://schema.registry.url:8082',
  'value.format' = 'avro-confluent',
  'value.fields-include' = 'EXCEPT_KEY'
);

Table Photographers dùng avro-confluent value format thay vì JSON — Flink table job tự động deserialize Avro data từ Kafka topic dùng schema information từ Confluent Schema Registry. Đây là pattern phổ biến trong production: schema registry đảm bảo compatibility, Flink SQL tự động handle deserialization.

Về metadata catalog: Flink hỗ trợ nhiều catalog type (JDBC-based, Apache Hive). Spark hỗ trợ local catalog và Hive. Trong production, bạn sẽ cần Hive hoặc Hive-compatible catalog để duy trì durable metadata — cho phép query thấy tất cả available table sau khi job restart.

Khai Báo Output Table Và JOIN Query

CREATE TABLE Enriched_Photographs (
  id BIGINT PRIMARY KEY NOT ENFORCED,
  photographer_id BIGINT NOT NULL,
  camera_id BIGINT NOT NULL,
  photo_url STRING NOT NULL,
  height INT,
  width INT,
  first_name STRING,
  last_name STRING
) WITH (
  'connector' = 'upsert-kafka',
  'topic' = 'Enriched_Photographs',
  ...
);

INSERT INTO Enriched_Photographs
  SELECT pics.id,
         pics.photographer_id,
         pics.camera_id,
         pics.photo_url,
         pics.height,
         pics.width,
         people.first_name,
         people.last_name
  FROM Photographs AS pics
  INNER JOIN Photographers AS people
  WHERE pics.photographer_id = people.kafka_key_id;

Kết quả join được ghi liên tục vào Enriched_Photographs topic. State về photograph và photographer được giữ vô thời hạn trong Flink job (mirroring key-space của source topic). Tombstone event trên bất kỳ source topic nào sẽ propagate deletion sang Enriched_Photographs — đảm bảo lifecycle consistency.

Bốn Cách Thực Thi Streaming SQL Code

1. Command-Line Interface (CLI)

Flink cung cấp ./bin/sql-client.sh, Spark cung cấp ./bin/spark-sql. Đây là cách đơn giản nhất để test và phát triển local. Bạn type SQL query vào CLI và thấy kết quả ngay lập tức.

flink-2.0.0 ./bin/sql-client.sh
Flink SQL>
> SELECT *
> FROM Photographs
> WHERE first_name = "Adam"
> AND last_name = "Bellemare";

Streaming SQL query yêu cầu CLI chạy vô thời hạn — nếu bạn terminate CLI, bạn terminate job. Dù vậy, CLI hoàn toàn có thể chạy trong container như microservice thông thường. Tuy nhiên, với production workload, các option phía sau thường phù hợp hơn.

2. Embedded SQL Trong Application

Nhúng SQL query trực tiếp vào native application code. Ví dụ Flink với Java:

// Tạo Flink table environment
TableEnvironment tableEnv = TableEnvironment.create(...);

// Chỉ định catalog và database bên ngoài
tableEnv.useCatalog("hive_ext");
tableEnv.useDatabase("photo_db");

// Tạo Photographs table bằng SQL DDL
// (metadata được ghi vào Hive catalog)
tableEnv.executeSql(
    "CREATE TABLE Photographs (id BIGINT ...) WITH (...)");

// Query Photographs table bằng SQL
tableEnv.executeSql(
    "SELECT * from Photographs where first_name = 'Alice'");

Embedded SQL tích hợp tốt với microservice deployment pipeline — test, CI/CD, scaling, monitoring đều được quản lý như microservice thông thường. Hạn chế là bị giới hạn bởi ngôn ngữ framework hỗ trợ (Java, Python, v.v.). Code generator có thể tự động tạo boilerplate và dependency, để team chỉ cần viết SQL logic.

3. Notebooks (Zeppelin, Jupyter)

Notebook là môi trường interactive browser-based kết hợp code thực thi, rich text, equations, và visualization. Data analyst và data scientist từ lâu đã dùng notebook (Apache Zeppelin, Jupyter) để explore dữ liệu và build transformation pipeline. Interpreter bridge notebook với processing engine bên dưới (ví dụ: Apache Zeppelin interpreter for Flink).

Ưu điểm của notebook: interactive development (viết, chạy, sửa code theo từng cell nhỏ, thấy kết quả ngay), visualization và documentation (kết hợp code với Markdown và chart), isolation (include environment details và hardcoded data), multilanguage support (Python, Java, Scala, R), và shareable (download và chia sẻ như file bình thường).

Nhược điểm cần lưu ý: version control phức tạp (file lớn, binary data khó integrate với Git — dùng nbdime hoặc nbstripout để giảm thiểu), performance hạn chế (không phải giải pháp hiệu quả nhất cho large-scale data), testing hạn chế (không phù hợp cho unit/integration test), promotion khó khăn (promote và rollback notebook giữa environments phức tạp).

Thực tiễn tốt: Notebook tối ưu cho exploration và analysis. Với production use case, extract logic ra một dedicated microservice project đầy đủ với unit/integration testing framework.

4. SQL Gateway

SQL gateway là service cho phép nhiều client thực thi SQL code đồng thời và từ xa. Client submit job đến gateway, gateway thực thi trong session riêng của nó. Nhiều session độc lập có thể chạy song song trong cùng gateway, tất cả dùng chung processing cluster.

Hình 14-2: Hai client kết nối đến SQL gateway — một client submit job mới, client kia get status của job đang chạy. Gateway quản lý nhiều session, tất cả dispatch đến processing cluster. Catalog chứa table definitions được share giữa tất cả session.

Ví dụ: Spark distributed SQL engine, Flink SQL gateway. Phù hợp nhất cho các SQL query đơn giản, ít thay đổi theo thời gian — ví dụ joiner service để denormalize relational data. Lợi ích: không cần tạo full application chỉ để chạy một query đơn giản.

SQL Như Một Sidecar

Streaming SQL có thể đóng vai trò SQL sidecar — một pattern mạnh mẽ cho phép tận dụng SQL cho phần xử lý phức tạp trong khi giữ business logic trong microservice framework ưa thích.

Hình 14-3 minh họa: Enriched_photographs stream và Cameras stream được fed vào một SQL joiner. SQL joiner tạo ra Private_Stream_F2AZ — đây là private internal stream chỉ dùng nội bộ trong bounded context. Microservice đọc từ Private_Stream_F2AZ và thực hiện business logic.

Tên Private_Stream_F2AZ là tên placeholder ngẫu nhiên — chủ ý tránh tên có ý nghĩa để nhắc nhở rằng đây là internal stream không được dùng bởi service nào khác bên ngoài bounded context này.

Lợi ích của SQL sidecar: bạn có thể dùng bất kỳ thư viện, ngôn ngữ, hay framework nào tương thích với basic event consumption/production cho microservice, trong khi offload joins/windowing/aggregation/complex state machine sang SQL engine. Microservice nhận dữ liệu đã được enrich và processed sẵn, chỉ cần lo business logic thuần túy.

Cảnh báo: Khi terminate microservice, đảm bảo SQL job cũng được terminate. Zombie SQL process sẽ tiếp tục chạy và consume resource. SQL joiner và microservice phải được quản lý lifecycle tightly coupled.

User-Defined Function (UDF)

Khi business logic không thể biểu diễn thuần túy bằng SQL syntax, Streaming SQL framework cho phép định nghĩa User-Defined Function (UDF) — viết bằng ngôn ngữ native của framework (Java cho Flink, Python/Scala cho Spark) và gọi inline trong SQL code.

Ví dụ: UDF đơn giản trong Flink Java thêm _modified vào string value:

import org.apache.flink.table.functions.ScalarFunction;

public class AppendModifiedUDF extends ScalarFunction {
  public String eval(String input) {
    if (input == null) {
      return null;
    }
    // Thêm '_modified' vào cuối input string
    return input + "_modified";
  }
}

Đây là scalar UDF (input 1 record → output 1 record). Có ba loại UDF chính:

  • Scalar UDF: Input 1 record → output 1 record (như ví dụ trên). Dùng để transform giá trị.
  • Aggregate UDF (UDAF): Input N records → output 1 aggregated record. Dùng để build aggregation phức tạp (ví dụ median, percentile, custom window function).
  • Table UDF (UDTF): Input 1 record → output N records. Dùng để explode một record thành nhiều record (ví dụ unnest array).

UDF không chỉ transform data — bạn có thể dùng UDF để xây dựng aggregation, complex state machine dựa trên record data, và thậm chí gọi external system: tích hợp với third-party service, gọi GenAI model để classify hoặc enrich data inline trong SQL pipeline.

Tổng Kết

Streaming SQL đơn giản hóa việc build microservice-like query thông qua cơ chế khai báo quen thuộc với bất kỳ ai biết SQL. Thay vì viết boilerplate code để consume event, manage state, và produce output, bạn chỉ cần mô tả kết quả mong muốn — SQL engine lo implementation.

Khái niệm cốt lõi là continuous query: query chạy vô thời hạn trên stream dữ liệu, áp dụng logic cho mỗi event đến. Stream-as-table abstraction (upsert, append-only, retraction table) là bước chuyển đổi then chốt giúp SQL làm việc với streaming data.

Bốn cách thực thi — CLI, embedded SQL, notebook, SQL gateway — phục vụ các giai đoạn khác nhau từ development đến production. UDF điền vào khoảng trống khi SQL thuần túy không đủ — cho phép custom logic, aggregation phức tạp, và tích hợp external system.

Flink SQL và Spark SQL là hai implementation chính, mỗi cái có thế mạnh riêng. Streaming SQL thường được cung cấp như một phần của serverless framework — chương tiếp theo sẽ xem xét Functions as a Service (FaaS), một serverless option khác trong kiến trúc event-driven.
