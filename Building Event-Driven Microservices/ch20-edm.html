Kiểm Thử Event-Driven Microservices

Unit testing, topology testing, schema evolution testing, integration testing với Testcontainers — từ hàm đơn lẻ đến toàn bộ hệ thống phân tán

← Chương 19: Công Cụ Hỗ Trợ Chương 21: Triển Khai →

Kiểm thử microservices hướng sự kiện vừa dễ hơn, vừa khó hơn so với kiểm thử hệ thống monolithic. Dễ hơn vì ranh giới của mỗi service được định nghĩa rõ ràng qua event stream, các test case có thể được tạo bằng cách inject event cụ thể và kiểm tra output. Khó hơn vì có nhiều lớp cần kiểm thử: từ hàm xử lý đơn lẻ, toàn bộ topology, schema evolution, cho đến integration với broker và các service khác. Chương này đi qua toàn bộ các lớp đó theo thứ tự từ đơn giản đến phức tạp.

Nguyên Tắc Kiểm Thử Chung

Có hai loại kiểm thử lớn: functional testing (kiểm tra tính đúng đắn của logic nghiệp vụ) và nonfunctional testing (kiểm tra các tính chất phi chức năng như hiệu suất và khả năng phục hồi).

Các loại functional testing:

  • Unit testing — kiểm thử từng hàm, component riêng lẻ với input/output xác định. Nhanh, không phụ thuộc external services.
  • Integration testing — kiểm thử nhiều component phối hợp với nhau, thường cần broker, database, hoặc schema registry thực.
  • System testing — kiểm thử toàn bộ hệ thống end-to-end trong môi trường giống production nhất có thể.
  • Regression testing — kiểm thử rằng các thay đổi mới không phá vỡ behavior đã có.

Các loại nonfunctional testing:

  • Performance testing — đo throughput, latency của service dưới tải bình thường.
  • Load testing — kiểm tra hành vi dưới tải cao (peak load).
  • Stress testing — đẩy hệ thống vượt giới hạn để tìm điểm gãy.
  • Recovery testing — kiểm tra khả năng phục hồi sau khi failures.

Unit Testing Hàm Stateless

Hàm stateless là hàm không phụ thuộc trạng thái bên ngoài — output chỉ phụ thuộc vào input. Đây là loại dễ test nhất.

Ví dụ: hàm myFilterFunction lọc các event theo điều kiện:

// Hàm cần test
boolean myFilterFunction(String key, MyEvent event) {
    return event.getValue() > 0 && event.getStatus().equals("ACTIVE");
}

// Unit test
@Test
void shouldReturnTrueForPositiveActiveEvent() {
    MyEvent event = new MyEvent("ACTIVE", 42);
    assertTrue(myFilterFunction("key1", event));
}

@Test
void shouldReturnFalseForNegativeValue() {
    MyEvent event = new MyEvent("ACTIVE", -1);
    assertFalse(myFilterFunction("key1", event));
}

@Test
void shouldReturnFalseForInactiveStatus() {
    MyEvent event = new MyEvent("INACTIVE", 42);
    assertFalse(myFilterFunction("key1", event));
}

@Test
void shouldReturnFalseForZeroValue() {
    MyEvent event = new MyEvent("ACTIVE", 0);
    assertFalse(myFilterFunction("key1", event));  // boundary case: 0 không > 0
}

Các boundary case đặc biệt quan trọng: giá trị 0 (zero boundary), null, string rỗng, giá trị tối đa/tối thiểu của type. Test phải cover cả các trường hợp biên này để tránh lỗi production khó debug.

Unit Testing Hàm Stateful

Hàm stateful đọc/ghi vào một datastore bên ngoài (state store, database). Để test đơn vị, cần mock datastore để tránh phụ thuộc vào infrastructure thực.

// Hàm cần test
void addValueToAggregation(String key, Long value, KeyValueStore<String, Long> store) {
    Long currentValue = store.get(key);
    if (currentValue == null) currentValue = 0L;
    store.put(key, currentValue + value);
}

// Unit test với mock store
@Test
void shouldInitializeAndAccumulateValues() {
    KeyValueStore<String, Long> mockStore = mock(KeyValueStore.class);

    // Lần đầu: store trống, currentValue = null
    when(mockStore.get("user-1")).thenReturn(null);
    addValueToAggregation("user-1", 10L, mockStore);
    verify(mockStore).put("user-1", 10L);

    // Lần thứ hai: store có giá trị cũ = 10
    when(mockStore.get("user-1")).thenReturn(10L);
    addValueToAggregation("user-1", 5L, mockStore);
    verify(mockStore).put("user-1", 15L);
}

Mock-based unit tests nhanh và không cần broker hay database thực, nhưng không đảm bảo behavior đúng khi tích hợp với state store thực. Cần bổ sung integration test cho các hàm stateful phức tạp.

Kiểm Thử Toàn Bộ Topology

Mỗi framework stream processing cung cấp công cụ để test toàn bộ topology xử lý event mà không cần broker thực:

  • Kafka Streams: TopologyTestDriver — chạy toàn bộ topology trong JVM, không cần Kafka broker. Hỗ trợ TestInputTopic để inject events và TestOutputTopic để đọc output.
  • Apache Flink: MiniClusterWithClientResource — mini Flink cluster chạy trong JVM test.
  • Apache Spark Streaming: StreamingSuiteBase — base class để test Spark streaming jobs.

Example 20-1: Kiểm Thử Với TopologyTestDriver

public class SumTopologyTest {

    private TopologyTestDriver testDriver;
    private TestInputTopic<String, Long> input;
    private TestOutputTopic<String, Long> output;

    // buildMyTopology: đọc từ "input-topic",
    // map, groupByKey, reduce (sum), ghi ra "output-topic"
    private Topology buildMyTopology() {
        StreamsBuilder builder = new StreamsBuilder();
        builder.stream("input-topic", Consumed.with(Serdes.String(), Serdes.Long()))
               .groupByKey()
               .reduce(Long::sum)
               .toStream()
               .to("output-topic", Produced.with(Serdes.String(), Serdes.Long()));
        return builder.build();
    }

    @Before
    public void setup() {
        Properties props = new Properties();
        props.put(StreamsConfig.APPLICATION_ID_CONFIG, "test-app");
        props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "dummy:9092");
        props.put(StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG,
                  Serdes.String().getClass());
        props.put(StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG,
                  Serdes.Long().getClass());

        testDriver = new TopologyTestDriver(buildMyTopology(), props);
        input = testDriver.createInputTopic("input-topic",
                          new StringSerializer(), new LongSerializer());
        output = testDriver.createOutputTopic("output-topic",
                           new StringDeserializer(), new LongDeserializer());
    }

    @Test
    public void shouldSumToThree() {
        input.pipeInput("a", 1L);
        input.pipeInput("a", 2L);

        assertThat(output.readKeyValue(),
                   equalTo(KeyValue.pair("a", 3L)));
        assertTrue(output.isEmpty());
    }

    @After
    public void teardown() {
        testDriver.close();
    }
}

TopologyTestDriver không cần Kafka broker thực — nó chạy topology hoàn toàn in-memory, kể cả state store. Điều này làm cho test cực kỳ nhanh và có thể chạy trong CI pipeline mà không cần Docker hay external services. Tuy nhiên, có những hành vi chỉ xuất hiện khi có broker thực (partition rebalancing, network latency) mà TopologyTestDriver không thể mô phỏng.

Kiểm Thử Schema Evolution

Schema evolution testing đảm bảo rằng khi producer thay đổi schema, các consumer với schema cũ vẫn có thể đọc được event mới (và ngược lại). Điều này được test trực tiếp với schema registry.

Quy Trình Test Bằng curl

Ví dụ kiểm tra tính tương thích của schema mới trước khi deploy:

# Example 20-2: Lấy schema hiện tại của topic
curl -X GET http://schema-registry:8081/subjects/my-topic-value/versions/latest

# Example 20-3: Đăng ký schema mới (version 2)
curl -X POST http://schema-registry:8081/subjects/my-topic-value/versions \
  -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  -d '{"schema": "{\"type\":\"record\",\"name\":\"MyEvent\",
        \"fields\":[{\"name\":\"id\",\"type\":\"string\"},
                    {\"name\":\"value\",\"type\":\"long\"},
                    {\"name\":\"newField\",\"type\":[\"null\",\"string\"],
                     \"default\":null}]}"}'

# Example 20-4: Kiểm tra tính tương thích của schema mới
curl -X POST \
  http://schema-registry:8081/compatibility/subjects/my-topic-value/versions/latest \
  -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  -d '{"schema": "..."}'
# Kết quả: {"is_compatible":true}

# Example 20-5: Xác nhận schema evolution rule hiện tại
curl -X GET http://schema-registry:8081/config/my-topic-value
# Kết quả: {"compatibilityLevel":"BACKWARD"}

Các bước này nên được tích hợp vào CI pipeline: trước khi merge code thay đổi schema, CI tự động test tính tương thích với schema registry. Nếu không tương thích, build fails ngay ở pipeline thay vì lỗi production.

Integration Testing

Integration testing kiểm thử service trong môi trường gần với production hơn: có broker thực, schema registry thực, và các dependent services.

Local Integration Testing

Có thể tạo môi trường integration test hoàn chỉnh trong JVM test bằng cách nhúng broker và schema registry:

// Example 20-6: Test với in-JVM broker và schema registry
public class IntegrationTest {

    // In-JVM Kafka broker (ví dụ: EmbeddedKafkaCluster)
    @ClassRule
    public static final EmbeddedKafkaCluster cluster =
        new EmbeddedKafkaCluster(1);  // 1 broker

    // Mock schema registry hoặc embedded schema registry
    private SchemaRegistryClient schemaRegistryClient;

    @Before
    public void setup() throws Exception {
        cluster.createTopic("input-topic");
        cluster.createTopic("output-topic");
        schemaRegistryClient = new MockSchemaRegistryClient();

        // Khởi tạo và start 2 instances của topology
        Properties props1 = buildStreamsProps(cluster.bootstrapServers(), "app-1");
        Properties props2 = buildStreamsProps(cluster.bootstrapServers(), "app-2");

        KafkaStreams streams1 = new KafkaStreams(buildTopology(), props1);
        KafkaStreams streams2 = new KafkaStreams(buildTopology(), props2);

        streams1.start();
        streams2.start();
    }

    @Test
    public void shouldProcessEventsCorrectly() throws Exception {
        // Produce events vào input-topic
        produceEvent("input-topic", "key1", new MyEvent("value1"));

        // Đợi output và kiểm tra
        ConsumerRecords<String, MyEvent> records =
            consumeWithTimeout("output-topic", Duration.ofSeconds(10));
        assertEquals(1, records.count());
        assertEquals("value1", records.iterator().next().value().getData());
    }
}

Container-Based Integration Testing Với Testcontainers

Testcontainers cho phép tạo và quản lý Docker containers trong JVM test, cung cấp môi trường integration testing giống production hơn in-JVM broker:

// Example 20-7: Testcontainers với Kafka, PostgreSQL, và Vault
public class ContainerIntegrationTest {

    @ClassRule
    public static KafkaContainer kafka =
        new KafkaContainer(DockerImageName.parse("confluentinc/cp-kafka:7.5.0"));

    @ClassRule
    public static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>(DockerImageName.parse("postgres:15"))
            .withDatabaseName("testdb")
            .withUsername("test")
            .withPassword("test");

    @ClassRule
    public static VaultContainer<?> vault =
        new VaultContainer<>(DockerImageName.parse("vault:1.15"))
            .withVaultToken("test-root-token");

    @Before
    public void configureVaultTransitSecrets() {
        // Kích hoạt transit secrets engine trong Vault để encrypt event fields
        VaultTransitOperations transit = vaultTemplate().opsForTransit();
        transit.createKey("my-encryption-key");
    }

    @Test
    public void shouldEncryptSensitiveFieldsInEvents() {
        // Test rằng PII fields được encrypt trước khi ghi vào Kafka
        String ssn = "123-45-6789";
        produceEventWithEncryption(kafka.getBootstrapServers(),
                                   vault.getHttpHostAddress(),
                                   ssn);

        ConsumerRecord<String, String> record =
            consumeNextRecord(kafka.getBootstrapServers(), "secure-topic");

        // Confirm SSN được encrypt, không phải plaintext
        assertNotEquals(ssn, extractSsnFromRecord(record));
        assertTrue(extractSsnFromRecord(record).startsWith("vault:v1:"));
    }
}

Testcontainers có ưu điểm lớn: containers được spin up và tear down tự động, môi trường test gần giống production, và test hoàn toàn isolated giữa các runs. Chi phí là thời gian khởi động container (~5-30 giây).

Figure 20-1: Lightweight Framework Với Containerized Dependencies

Trong kiến trúc lightweight framework (như Kafka Streams), microservice chạy trong một JVM process. Integration testing có thể được thực hiện bằng cách tạo containers cho các dependencies:

[Test Process]
  ├─ Kafka container (event broker)
  ├─ Schema Registry container
  ├─ State store container (nếu dùng external store)
  └─ Microservice instance (chạy trong test process)

Figure 20-2: Heavyweight Framework Containerized

Với heavyweight frameworks (Flink, Spark), cần containerize cả framework cluster:

[Test Environment]
  ├─ Kafka container
  ├─ Schema Registry container
  ├─ Flink/Spark cluster container (JobManager + TaskManagers)
  └─ Microservice job được submit lên cluster container

Môi trường này phức tạp hơn nhưng mô phỏng chính xác hơn cách service chạy trong production.

Kiểm Thử Với Fully Remote Cloud Services

Thay vì tạo infrastructure local hoặc container, có thể test trên cloud services thực. Có ba chiến lược, từ tốt nhất đến kém nhất:

1. Temporary Single-Tenant Environment (Tốt Nhất)

Tạo một môi trường cloud hoàn chỉnh, riêng biệt cho mỗi test run. Sau khi test xong, môi trường được xóa.

  • Ưu điểm: hoàn toàn isolated, không có multitenancy issues, giống production nhất.
  • Nhược điểm: chi phí cloud cao hơn, thời gian provisioning lâu hơn.
  • Khi nào dùng: integration testing quan trọng trước deployment, performance testing cần môi trường sạch.

Môi trường tạm thời có thể được populate với một curated testing source — một snapshot của production data đã được anonymize và sanitize để phù hợp cho testing.

2. Durable Multitenant Environment (Kém Nhất)

Nhiều team chia sẻ một môi trường staging duy nhất chạy liên tục.

  • Ưu điểm: chi phí thấp hơn vì chia sẻ infrastructure.
  • Nhược điểm: "tragedy of the commons" — mỗi team có thể làm ô nhiễm môi trường chung; test data bị contaminate; resource contention giữa các teams.
  • Thực tế: team A break schema gây lỗi cho team B; team C flood broker gây latency spike cho team D. Overhead để maintain môi trường shared rất cao.

3. Production Environment (Chỉ Smoke Tests)

Test trực tiếp trên production với lưu lượng thực.

  • Khi nào phù hợp: smoke tests — kiểm tra nhanh sau deployment rằng service cơ bản hoạt động, không phải test đầy đủ.
  • Không nên: regression tests, performance tests, hay bất kỳ test nào có thể gây side effects cho production data.

Ngoài ra, môi trường cloud tạm thời có thể dùng cho performance và load testing: tạo environment, chạy production-like load để đo throughput và latency, sau đó tear down. Kết quả được lưu trữ để tracking theo thời gian.

Chiến Lược Chọn Môi Trường Test

Không có một chiến lược đúng cho mọi trường hợp. Quyết định phụ thuộc vào:

  • Quy mô tổ chức: startup nhỏ có thể dùng môi trường shared; enterprise lớn cần isolated environments.
  • Tính chất service: service stateless dễ test hơn service stateful phức tạp với nhiều input streams.
  • SLA yêu cầu: service mission-critical cần testing environment giống production nhất.
  • Ngân sách: temporary single-tenant tốt nhất nhưng tốn kém nhất.

Nguyên tắc tổng quát: môi trường test shared có overhead cao vì phải maintain và debug khi bị contaminate. Môi trường disposable (tạm thời) đòi hỏi đầu tư ban đầu vào automation nhưng cho isolation tốt hơn và ít overhead về lâu dài.

Tóm Tắt

Kiểm thử event-driven microservices đòi hỏi một chiến lược nhiều lớp. Unit test kiểm tra logic từng hàm riêng lẻ — stateless functions thì đơn giản, stateful functions cần mock datastore. TopologyTestDriver (Kafka Streams), MiniClusterWithClientResource (Flink), và StreamingSuiteBase (Spark) cho phép test toàn bộ topology mà không cần broker thực, với tốc độ nhanh phù hợp cho CI. Schema evolution testing dùng curl hoặc SDK để verify tính tương thích với schema registry, nên được tích hợp vào CI pipeline.

Integration testing với Testcontainers cho phép tạo môi trường isolation hoàn chỉnh với Kafka, PostgreSQL, Vault thực trong Docker containers. Đối với testing ở quy mô lớn hơn, temporary single-tenant cloud environment là lựa chọn tốt nhất — isolation hoàn toàn, không có multitenancy issues — mặc dù tốn kém hơn durable shared environment. Sự đầu tư vào automation để tạo môi trường disposable sẽ trả lại rất nhiều lần qua việc giảm overhead debugging và tăng độ tin cậy của test results.
